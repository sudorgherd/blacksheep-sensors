# v0.2.0 Stage 2 — Frame Layout and Packet-Class Validation

**Status:** Complete
**Version:** `0.2.0-dev`
**Stage boundary:** structural MAC-header layout only; no address semantics

## Objective and authorities

Stage 2 answers which standard-defined 802.11 MAC-header shape a safely copied
prefix represents and how many bytes must exist before that layout is complete.
It does not interpret any address.

The implementation was checked against IEEE Std 802.11-2020 clause 9.2 Frame
formats and its management, control, Block Ack, and data frame-format clauses;
the public Linux `include/linux/ieee80211.h` and `ieee80211-ht.h` definitions
that cite those clauses; and ESP-IDF 5.5.4's public callback classes and bundled
`wpa_supplicant/src/common/ieee802_11_defs.h`. IEEE layout, ESP-IDF callback
classification, and BLACKSHEEP fail-closed policy remain separate contracts.

## Descriptor contract

`wifi_layout_result_t` retains Stage 1 status and frame-control validity and now
adds a layout kind plus structural presence flags for Addr1–Addr4, QoS Control,
HT Control, BAR Control, and a compressed BA bitmap. Address flags mean only
that bytes occupy the standard layout. They do not name receiver, transmitter,
source, destination, or BSSID roles.

### Management

Subtypes 0–5 and 8–14 are supported. Subtypes 6, 7, and 15 are explicit
reserved values. A supported management header requires 24 bytes, or 28 when
the management Order bit indicates the four-byte HT Control field. No body or
information element is accessed.

### Control

| Subtype | Layout | Required bytes |
| --- | --- | ---: |
| 7 Control Wrapper | RA, Carried FC, HT Control | 16 |
| 8 Block Ack Request | non-Multi-TID BAR Control and Starting Sequence Control | 20 |
| 9 Block Ack | compressed, non-Multi-TID bitmap form | 28 |
| 10 PS-Poll | two-address control | 16 |
| 11 RTS | two-address control | 16 |
| 12 CTS | one-address control | 10 |
| 13 ACK | one-address control | 10 |
| 14 CF-End | two-address control | 16 |
| 15 CF-End + CF-Ack | two-address control | 16 |

BAR/BA parsing first requires 18 bytes so the BAR/BA Control discriminator can
be read safely. Multi-TID forms are `UNSUPPORTED_EXTENSION`. Basic BA requires
148 bytes and therefore is also `UNSUPPORTED_EXTENSION`; it is never truncated
to the 40-byte project prefix or assigned a plausible shorter size. Trigger
frames and Control Frame Extensions are explicit unsupported subtypes because
their layouts are variable/extension-dependent. Unassigned control encodings
are explicit reserved subtypes.

### Data, QoS, Addr4, and HT Control

All 16 data subtype encodings use the same structural calculation. The base is
24 bytes. To DS=1 and From DS=1 adds six bytes for Addr4. A subtype with bit 3
set adds two bytes for QoS Control. Only a QoS data layout with Order set adds
four bytes for HT Control. Order on ordinary non-QoS data does not globally add
four bytes. Resulting supported minima are 24, 26, 30, 32, 30, 34, or 36 bytes
depending on the structural combination, all within the unchanged 40-byte
capture bound.

## Failure and class-comparison behavior

Every read is preceded by a length check. Zero/one-byte input is truncated;
nonzero protocol versions are invalid; type 3 is unsupported; and reserved,
unsupported subtype, and unsupported extension remain distinct. A BAR/BA frame
shorter than its 18-byte discriminator boundary exposes no guessed final
length.

The pure class comparator produces agreement, mismatch, no-parse/truncated,
unsupported/reserved, MISC-with-no-payload, or invalid. Firmware counts these
outcomes. A mismatch prevents the worker event from being accepted as a parsed
layout. MISC never enters payload parsing.

## Host verification

The strict C11 host suite passed **241,942 assertions**. It includes every
supported management representation, every supported control descriptor,
reserved and unsupported control cases, all 16 data subtypes across all four
To DS/From DS combinations, QoS, Addr4, management and QoS HT Control, deliberate
class mismatches, Stage 1 queue/copy regression, and programmatic lengths zero
through each supported required length minus one. The suite also passed
100,000 deterministic randomized byte sequences of lengths 0–40 with randomized
callback classes and invariants on status, flags, and maximum required length.

MinGW still lacks `libasan` and `libubsan`, so sanitizer linking was unavailable
as in Stage 1. The identical suite passed with `-std=c11 -Wall -Wextra -Werror
-pedantic -O2`; no global package was installed.

## Physical evidence

Both finite windows used the assigned fixed role/channel and an owned second C5
as a disposable raw data-frame source. The transmitter submitted a fixed
synthetic 1000-byte non-QoS data frame at the controlled stress cadence. Its
project stayed under ignored `.pio` storage and is not a repository artifact.
No address, SSID, payload, or packet body was printed or retained.

### C5 #1 — 2.4 GHz

USB identity ended `9E:88`; its rediscovered temporary port was COM6. Channel 1
and 2.4-GHz-only mode were verified. Upload/hash, ESP-IDF second-stage boot,
ESP32-C5 revision 1.2, QIO/80 MHz, 32 MB flash, and 8 MB PSRAM test passed.

The eight-second window produced 754 callbacks, enqueues, processed events, and
class agreements; queue high-water was 1 and drops were 0. Parser results were
754 OK with zero truncated, unsupported, reserved, unsupported-extension,
invalid, or mismatch. Observed layouts were 28 management subtype 4 frames and
726 data subtype 0 frames. QoS, Addr4, HT Control, and control subtypes were not
observed. Callback timing was 6/51/6 microseconds minimum/maximum/average.
Drain and Wi-Fi shutdown passed, READY returned, and five subsequent heartbeats
were observed.

### C5 #2 — 5 GHz

USB identity ended `AC:6C`; its rediscovered temporary port was COM7. Manual US
regulatory context, channel 36, and 5-GHz-only mode were verified. The same
upload, boot, flash, revision, and PSRAM baseline passed.

The eight-second window produced 898 callbacks, enqueues, processed events, and
class agreements; queue high-water was 1 and drops were 0. Parser results were
898 OK with zero truncated, unsupported, reserved, unsupported-extension,
invalid, or mismatch. Observed layouts were 142 management subtype 8 frames,
746 data subtype 0 frames, and 10 QoS data subtype 12 frames. Addr4, HT Control,
and control subtypes were not observed. Callback timing was 6/51/6 microseconds
minimum/maximum/average. Drain and shutdown passed, READY returned, and five
subsequent heartbeats were observed.

The observed management traffic establishes real management layout handling;
the owned transmitter establishes ordinary data parsing on both bands; and the
5 GHz sample additionally establishes a real QoS layout. There was 100% class
agreement in both bounded samples. Control Wrapper, BAR/BA, PS-Poll, RTS,
CTS/ACK, CF-End variants, Addr4, and HT Control remain physically **NOT
OBSERVED** and exhaustively host-validated where supported. Physical absence is
not treated as failure.

## Unresolved questions

Physical prevalence of control, Addr4/WDS, and HT Control layouts remains
unmeasured. Newer Trigger/Control Extension and Multi-TID/large BA variants are
deliberately unsupported until a bounded discovery need and authoritative
variant model justify them. These limits do not cause guessing and do not block
Stage 2.
