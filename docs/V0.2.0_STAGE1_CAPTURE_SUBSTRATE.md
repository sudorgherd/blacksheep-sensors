# v0.2.0 Stage 1 — Capture Substrate Evidence

**Status:** Stage 1 implementation and acceptance evidence complete.

## Contract and architecture

The installed ESP-IDF 5.5.4 public headers define management, control, and data
callbacks as `wifi_promiscuous_pkt_t` (RX metadata followed by a zero-length
payload member) and MISC callbacks as receive-control metadata only. They do
not guarantee that the callback buffer survives callback return. BLACKSHEEP
therefore treats the buffer as callback-lifetime-only: all required metadata
and bytes are copied synchronously and no raw or payload pointer escapes.

`wifi_capture_event_t` contains normalized RSSI, noise floor, primary and
secondary channel, driver timestamp, `sig_len`, `dump_len`, receive states,
callback class, captured length, validity/discrepancy flags, a diagnostic event
number, and a fixed 40-byte prefix. It contains no pointer, payload body, parsed
identifier, or persistent data. Its measured C ABI size is 72 bytes.

The firmware uses a static FreeRTOS queue with 128 entries in internal DRAM.
Event storage costs 9,216 bytes, plus the implementation's `StaticQueue_t`
control object. The equivalent host ring prototype is 9,256 bytes including
indices, state, and statistics. Enqueue uses zero ticks. A full queue drops the
newest event and increments a saturating 64-bit counter. Enqueue, dequeue,
drop, high-water, and current depth are bounded or directly observable.

The callback validates the buffer and class, handles MISC without payload
access, rejects failed RX states, copies normalized metadata, calculates the
bounded length, copies at most 40 bytes, attempts a zero-wait enqueue, records
bounded counters and duration, and returns. It does no printing, allocation,
semantic parsing, identifier handling, or payload processing. Duration uses
`esp_timer_get_time()` at entry and exit and is summarized only after capture.

The worker consumes and immediately releases events, runs only the shared
frame-control/layout parser and callback-class consistency check, and updates
aggregate result counters. It performs no Stage 2 semantic interpretation.

Shutdown sets the accepting gate false, disables promiscuous mode, unregisters
the callback, gives the worker up to two seconds to drain, boundedly counts and
discards any remainder on timeout, stops/deinitializes Wi-Fi, and resumes
READY/heartbeat operation. Queue storage is static and is never freed while a
callback or worker could reference it.

## Copy-length and FCS treatment

For non-MISC successful receptions, both public C5 lengths must be nonzero.
The copied length is exactly:

`min(sig_len, dump_len, 40)`

Unequal lengths increment the discrepancy counter. The implementation never
adds or subtracts four bytes and never reads beyond the smaller advertised
length.

The controlled source was the other owned ESP32-C5 running a disposable,
untracked ESP-IDF transmitter. It passed a compile-time 1,000-byte non-QoS data
frame to `esp_wifi_80211_tx()` 160 times on US channel 36; all 160 calls
succeeded. The buffer contains exactly 1,000 bytes and no FCS field. A standard
four-byte 802.11 FCS generated by the radio makes the independently expected
over-air MAC frame length 1,004 bytes. C5 #2 observed `sig_len` up to exactly
1,004 and `dump_len` up to exactly 1,008. All 398 frames in that bounded window
had `dump_len == sig_len + 4`. An earlier controlled 128-byte source on channel
1 similarly produced maxima of 132 and 136 bytes.

The experiment supports `sig_len` including the generated FCS for these
controlled frames. It does not establish what the additional four bytes
represented by `dump_len` mean, nor does public documentation guarantee that
they are delivered bytes. That final ambiguity remains explicit. Selecting the
smaller nonzero advertised length and capping it at 40 means the controlled
1,004/1,008 case still copies only 40 bytes. No speculative adjustment, pcap,
packet body retention, or identifier output was introduced.

## Host robustness results

`firmware/esp32-c5/test/host/run.ps1` compiles the pure C substrate with C11,
strict warnings, and attempts AddressSanitizer plus UndefinedBehaviorSanitizer.
The installed MinGW GCC lacks both sanitizer runtime libraries (`libasan` and
`libubsan`), so sanitizer linking was unavailable. The identical suite then
passed without sanitizers: **119,259 assertions**, including every length from
zero through the management-header boundary, reserved/unsupported values,
copy bounds, class consistency, empty/fill/overflow/drop-newest/drain/shutdown
queue behavior, saturation, and 100,000 deterministic randomized frames.

For every formal matrix run, failed RX, truncation, unsupported, invalid,
callback-class mismatch, counter saturation, and queue drops were zero. Every

neither board then reported a watchdog. This did not change production code or
the queue size.

## Stage 1 acceptance

The controlled known-length experiment and distinct quiet, representative, and
stress matrices are complete. The conservative copy rule remains demonstrably
bounded, both representative runs are below one-percent drops, the stress runs
remain bounded and stable, and shutdown/READY/heartbeat behavior passed on both
assigned roles. Stage 1 is **PASS**. The meaning and delivery contract of the
four bytes by which `dump_len` exceeds `sig_len` remains an explicitly bounded
driver ambiguity and does not block Stage 1.

Stage 2 parsing, semantic address roles, identifiers, sequence/retry/protected
semantics, payload retention, pcap output, observation schema, and later
milestone work were not implemented.
