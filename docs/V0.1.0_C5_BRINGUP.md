# v0.1.0 ESP32-C5 Bring-Up Record

**Status:** In progress; initial firmware/toolchain bring-up verified on both
N32R8 boards

## Hardware observed

Both connected devices report:

* ESP32-C5 revision 1.2
* 240 MHz single-core RISC-V processor with LP core
* 48 MHz crystal
* ESP32-C5-WROOM-1U module, shield marking `MDN32R8`
* N32R8 configuration: 32 MB Quad-SPI flash and 8 MB Quad-SPI PSRAM
* external-antenna WROOM-1U variant
* observed flash JEDEC manufacturer `0x20`, device `0x4019`
* native USB Serial/JTAG (`303A:1001`)

The module identity was read from Board 1's shield. The repository uses a local
PlatformIO manifest because the installed platform has no exact canned N32R8
target; it does not claim a DevKitC, XIAO, or other carrier-board identity.

## Development environment

* PlatformIO Core 6.1.19
* pioarduino Espressif32 platform 55.03.39 (pinned release URL)
* ESP-IDF 5.5.4
* RISC-V GCC toolchain 14.2.0+20260121
* esptool 5.3.0
* target: `esp32c5`, ESP32-C5-WROOM-1U-N32R8
* memory: 32 MB Quad-I/O flash and 8 MB Quad-SPI PSRAM at 80 MHz
* upload: `esptool` over native USB, 460800 baud
* monitor: native USB Serial/JTAG, 115200 baud, DTR/RTS inactive

ESP-IDF is used because the initial Arduino-ESP32 3.3.9 image built but entered
the same pre-application reset loop on Board 1. ESP-IDF is Espressif's supported
C5 baseline and removes the Arduino layer from further bring-up diagnosis.

## Build and upload procedure

From the repository root:

```powershell
platformio run -d firmware\esp32-c5
platformio run -d firmware\esp32-c5 -t upload --upload-port COM_PORT
Set-Location firmware\esp32-c5
platformio device monitor --port COM_PORT
```

Replace `COM_PORT` with the currently discovered port. Do not commit a port to
project configuration.

## Physical observations

### Board 1

Temporary assignment during this session: COM6, USB serial
`10:BD:A3:F3:9E:88`.

* chip and 32 MB flash detection: pass
* firmware upload and written-data verification: pass
* normal boot with the corrected repository workflow: pass
* second-stage bootloader, PSRAM test, application diagnostics, and heartbeat:
  pass

During diagnosis, the PlatformIO/SCons-produced bootloader repeatedly reported:

```text
rst:0x7 (TG0_WDT_HPSYS),boot:0x58 (SPI_FAST_FLASH_BOOT)
Core0 Saved PC:0x4003abb0
```

The loop occurs before `app_main`. It persisted with 80 MHz and 40 MHz DIO
flash settings, Arduino and ESP-IDF frameworks, USB-primary and UART-primary
console configurations, and DTR/RTS disabled. No application crash or watchdog
output was observed because application startup was never reached.

Those attempts predated physical identification of the N32R8 module and did not
enable its in-package Quad-SPI PSRAM. They are retained as historical evidence,
not as validation of the corrected N32R8 configuration.

On 2026-08-24, the corrected ESP-IDF image built successfully and its generated
configuration was inspected before upload. It selected `esp32c5`, QIO flash,
32 MB flash, 80 MHz flash, Quad PSRAM, 80 MHz PSRAM, boot-time PSRAM
initialization, fatal-on-missing behavior, and the startup PSRAM memory test.
Both the bootloader and application image headers identify ESP32-C5, 32 MB, and
80 MHz with valid checksums and hashes. Their headers say DIO intentionally:
ESP-IDF writes QIO/QOUT bootloaders in ROM-readable DIO mode, and the bootloader
then enables quad mode during initialization.

That image was uploaded to Board 1 on temporary port COM6. PlatformIO identified
ESP32-C5 revision 1.2 and auto-detected 32 MB flash. Its Windows output thread
then encountered a CP1252 progress-rendering error, so the command's reported
success was initially ambiguous. Subsequent monitoring showed the same repeated
ROM output as before, with no second-stage bootloader or application output:

```text
rst:0x7 (TG0_WDT_HPSYS),boot:0x58 (SPI_FAST_FLASH_BOOT)
Core0 Saved PC:0x4003abb0
```

Direct esptool readback on 2026-08-24 resolved that ambiguity. The generated
ESP-IDF `flash_args` and `flasher_args.json` metadata specify these regions:

| Region | Offset | Length | SHA-256 (local and readback) |
| --- | ---: | ---: | --- |
| Bootloader | `0x2000` | 23,168 bytes | `1B1550FB6C5859A7A5D128A406DDF47A793D7B1086B28B548E99A8BC50DA0CF6` |
| Partition table | `0x8000` | 3,072 bytes | `7F00B6C042A89B15B0CAC534F82ED988CAF29278FF5700B0C511EB1B5BB7C820` |
| Application | `0x10000` | 205,056 bytes | `8AF6A52F788C23F006432175003686083016B1A844911BB6253E6E965EFFB214` |

Each region was read from Board 1 on COM6 at its exact artifact length. Binary
comparison reported no differences for all three regions, and each readback
SHA-256 matched its local artifact. Direct reflashing was therefore unnecessary
and was not performed. The corrected N32R8 firmware is conclusively present in
flash, so the identical pre-boot watchdog loop is a real boot failure rather
than an incomplete PlatformIO upload.

An untouched official ESP-IDF 5.5.4 `hello_world` control subsequently booted
Board 1 normally. A controlled BLACKSHEEP A/B test then established the causal
boundary: PlatformIO's SCons integration regenerated the ESP-IDF bootloader and
that artifact failed during ROM startup, while the native ESP-IDF CMake-produced
bootloader from the same BLACKSHEEP configuration booted the second stage and
application successfully. Missing revision metadata alone was not proven to be
the cause.

The project-local `scripts/native_bootloader.py` PlatformIO hook now builds the
authoritative native CMake bootloader, replaces PlatformIO's upload artifact
after SCons regeneration, and verifies before upload that both files have the
same SHA-256. It also rejects images unless they identify ESP32-C5, DIO, 80 MHz,
32 MB flash, minimum revision v1.0, and maximum revision v1.99.

The final clean build produced identical native and selected bootloader SHA-256
values:

```text
ACD2FF3EAB03561C4184F43CB66F05DA6240C4B4AF825753568FE7A32AE07ED3
```

Using the corrected normal PlatformIO build/upload workflow, Board 1 completed
written-data verification at `0x2000`, `0x8000`, and `0x10000`, entered the
ESP-IDF 5.5.4 second-stage bootloader, enabled QIO at 80 MHz, reported 32 MB
flash, detected 8 MB PSRAM at 80 MHz, passed the PSRAM memory test, printed the
BLACKSHEEP `0.1.0-dev` banner and `Status: READY`, and sustained heartbeats 0
through 22 without a watchdog, panic, crash, or reset loop.

The successful corrected boot reported ROM `boot:0x58 (SPI_FAST_FLASH_BOOT)`,
demonstrating that this boot-state value alone was not the cause of the earlier
failure.

## Limitations and next step

The N32R8 manifest and ESP-IDF defaults now select 32 MB QIO flash, 8 MB QSPI
PSRAM, 80 MHz flash/PSRAM clocks, boot-time PSRAM initialization, and the PSRAM
memory test. A missing PSRAM is fatal rather than silently ignored. ESP32-C5 SPI
boot also requires GPIO28 high; GPIO26/GPIO27/GPIO28 are strapping pins, and
CHIP_PU must not float. These electrical boot requirements are carrier-board
properties and are not replaced by firmware settings.

Initial build, programming, boot, serial diagnostics, flash detection, and PSRAM
initialization are now verified on both boards. Remaining v0.1.0 work is 2.4 GHz
and 5 GHz Wi-Fi operation, passive/promiscuous observation, channel
selection/hopping, and Wi-Fi metadata characterization.

No Wi-Fi sensing, scanning, promiscuous mode, channel control, frame processing,
aggregation, or multi-board coordination is implemented.
